# v15.0.0

## NewHeap.Platform.AI.Chat and NewHeap.Platform.AI.Test: one retry after a transient provider error

A provider error inside the model stream is not covered by the provider's HTTP retry. When a
transient one (`server_is_overloaded`, `server_error` or `rate_limit_exceeded`) arrives before
the model wrote text or called a tool, the turn now waits two seconds and calls the model once
more, and logs that it did. A repeated or other provider error, or one after text or a tool
call, still ends the turn as `failed` with `assistant-model-unavailable`; the conversation
accepts the next message. `NhAiScriptedChatClient.RespondWithProviderError(errorCode, text)`
scripts such an error for tests.

## NewHeap.Platform.AI.Chat: live agent work for the person who starts a run by hand

`AgentWorkChanged` reached the thread's participants and the subject's member snapshot only. A
person who started an agent by hand (`POST threads/start` or `INhAssistantAgentTriggers.StartAsync`)
was neither until they opened the thread, and a thread in which only such starts and runs without
proposals had worked had no member snapshot at all. The run's start and end then reached nobody,
so the subject's suggestions and run timeline stayed on queued until a reload. Now the first
update of a thread without a member snapshot fills it through the subject access resolver, as the
first notification already did, and an update that names a run, about the run or one of its
proposals, also reaches the person who started that run while the resolver still gives them a role
on the subject, also when no member list names them.
A failing refresh or resolver call never stops the update. Shadow threads still reach only their
own audience.

| Adoption note | Required action |
|---|---|
| The first agent work update of a thread without a member snapshot calls `INhAiSubjectAccessResolver.ListMembersAsync`, and an update about a run that a person started calls `ResolveAsync` for that person, inside background operations as well. | Keep both resolver methods free of request-only state, as agent notifications already require. |
| A run started by hand now reports its start and end through `AgentWorkChanged`, also when it proposes nothing. | Reload on the update; keep polling such a run only as a fallback for a missing hub connection. |
| No migration, no configuration and no public API change. | None. |

## NewHeap.Platform.AI.Chat and NewHeap.Platform.AI.Chat.AspNet: skills and triggers as data

Skills, and the triggers that start them, can now be added to an agent configured in code as data,
without a deploy. Code registers the building blocks data names: `AddTriggerEvent<TEvent>(name, ...)`
with `NhAssistantTriggerEventBuilder` (subject, message, initiator, dedupe key, payload and filter of
every trigger on the event; one published event serves code and data triggers),
`AddSubjectSet(name, description, subjects)` for data schedules and
`AddRuleHandler<THandler>(name, description)` for data skills that work by rules. Names are dash-case
segments joined by dots, at most 100 characters. `INhAssistantAgentConfiguration` and the endpoints
`GET admin/run-catalog`, `GET admin/agents/{id}/configuration`, `PUT`/`DELETE
admin/agents/{id}/skills/{skillId}`, `GET admin/agents/{id}/skills/{skillId}/versions`,
`PUT`/`DELETE admin/agents/{id}/triggers/{triggerId}` and `POST
admin/agents/{id}/triggers/{triggerId}/shadow` store data skills (description, instructions with
their SHA-256 hash, tools within the agent's own selectors, profile, rule handler, ceiling, budget
and approval policy) and data triggers (an event or a schedule with cron, time zone, subject set and
message, the skill, conflict and debounce). Saving checks the data as startup checks code; skills
and triggers in code cannot change (`assistant-skill-in-code`, `assistant-trigger-in-code`), a skill
a data trigger names stays (`assistant-skill-in-use`) and an agent holds at most 20 skills and 20 data
triggers (`assistant-configuration-limit`). Grants never become data. A new skill and a new trigger
start in shadow; put the skill live with `SetSkillShadowAsync` and the trigger with
`SetTriggerShadowAsync`. A change of a skill is its next version, which takes effect at once; versions
stay as history. Changes are audited as `AdminAgentSkillDefinitionChanged` and
`AdminAgentTriggerDefinitionChanged`.

Every reader works on one snapshot of code and data, which reloads in every host when the run
configuration's stamp changed: checked before every fire and run start at most once per second and
every 30 seconds by a background service. Data schedules get Hangfire recurring jobs under the
prefix `nh-assistant-data-trigger-`. Data that no longer fits the code, such as a trigger on an event
a deploy removed, is left out of effect and listed under `problems` in the agent's configuration
instead of failing startup. `NhAssistantSkillOptions` gains `DataVersion` and `RuleHandlerName`.

Apply the `AgentRunConfiguration` migration of `NewHeap.Platform.AI.Chat.SqlServer` or
`NewHeap.Platform.AI.Chat.PostgreSql`: it adds the tables `AssistantAgentSkillDefinition`,
`AssistantAgentTriggerDefinition` and `AssistantRunConfigurationStamp`.

| Breaking change | Required action |
|---|---|
| Database schema change. | Apply the `AgentRunConfiguration` migration. |
| Hosts with agent runs read the run configuration's stamp before fires and run starts and every 30 seconds. | Nothing; apply the migration before the host starts firing triggers. |

## NewHeap.Platform.AI.Common, NewHeap.Platform.AI.AspNet.Common, NewHeap.Platform.AI.Chat and NewHeap.Platform.AI.Chat.AspNet: run settings as data and accountable rights

An agent created in the administration now runs on its own once it has run settings as data:
`INhAssistantAgentConfiguration.SaveRunSettingsAsync` and `RemoveRunSettingsAsync`, or `PUT` and
`DELETE admin/agents/{id}/run-settings`, set whom it answers to (`agent`, `subject-responsible` or
`service-account` with an account that exists and may sign in), its approval policy, budget, run
ceiling, retries, gateway reads, elevated reads, triage profile and rule handler by name. It then gets
data skills and data triggers like an agent in code, and `GET admin/agents/{id}/configuration`
returns them with `source` and `runSettings`. Grants never become data: in headless runs such an
agent acts with the rights of the person or technical account it answers to, within its tool
selectors. The invocation gate allows a tool when that account, rebuilt with `INhAiPrincipalFactory`,
passes the tool's policies, after the initiator's delegation and before grants, and records the new
grant source `NhAiGrantSource.Accountable` (`accountable` in the API); reads are shielded like a
grant's. `NhAiAgentInvocationScope.ActWithAccountableRights` carries the choice, and an agent in code
opts in with `NhAssistantAgentRunBuilder.ActWithAccountableRights()`, which startup refuses for an
agent that answers to itself. A thread of an administration agent follows a change of whom it
answers to. Changes are audited as `AdminAgentRunSettingsChanged`; an agent in code cannot get run
settings as data (`assistant-run-settings-in-code`) and settings stay while data skills or triggers
belong to the agent (`assistant-run-settings-in-use`). Hosts need `AddAssistantAgentRuns` for such
agents, as for agents in code.

Apply the `AgentRunSettings` migration of `NewHeap.Platform.AI.Chat.SqlServer` or
`NewHeap.Platform.AI.Chat.PostgreSql`: it adds the table `AssistantAgentRunConfiguration`.

| Breaking change | Required action |
|---|---|
| `NhAiGrantSource` has the new value `Accountable` (`accountable` in the API). | Handle it where you switch on grant sources, as you handle `Agent`. |
| `NhAssistantAgentConfigurationDto` has the new members `Source` and `RunSettings`. | Pass them when you construct the record in tests. |
| Database schema change. | Apply the `AgentRunSettings` migration. |

## NewHeap.Platform.AI.Chat and NewHeap.Platform.AI.Chat.AspNet: skill candidates in shadow

A change of a live data skill now chooses how it takes effect: `apply: "live"` (default) puts the next
version live at once; `apply: "shadow"` makes it the skill's candidate. A candidate takes every event
of the triggers that name its skill as a second run in the agent's shadow thread, next to the live
version's run, with its own inputs and its own rules, instructions, tools and profile, and nothing it
proposes executes. Routing by rules or triage reaches the live version. Promote it with
`PromoteSkillCandidateAsync` or `POST admin/agents/{id}/skills/{skillId}/candidate/promote`, discard
it with `DiscardSkillCandidateAsync` or `POST .../candidate/discard` (body `{ "version", "reason" }`),
and compare both with `CompareSkillCandidateAsync` or `GET .../candidate/comparison`: runs, outcomes,
usage and proposals per tool, the decisions about the live version's proposals and the events both
handled. A new version discards an earlier candidate; discarded versions stay as history with the
status `discarded`. Runs record `skillVersion` and `skillCandidate` (`NhAssistantRunDto`); a queued
candidate run whose candidate was discarded ends with `assistant-skill-version-gone`, and a skill
without a candidate answers `assistant-skill-candidate-not-found`. `NhAssistantDataSkillDto` gains
`Candidate`.

Apply the `AgentSkillCandidates` migration of `NewHeap.Platform.AI.Chat.SqlServer` or
`NewHeap.Platform.AI.Chat.PostgreSql`: it adds `SkillVersion` and `SkillCandidate` to
`AssistantRun` and `SkillCandidate` to `AssistantQueuedInput`.

| Breaking change | Required action |
|---|---|
| Database schema change. | Apply the `AgentSkillCandidates` migration. |
| A run of a candidate counts against the agent's and the skill's budget and run limits. | Allow for one extra run per event of the triggers that name a skill while it has a candidate. |
