# Agent Off State Plan

This document records the decisions behind three agent features: an **off** state for agents and
skills with a starting state in code (`StartsOff()`), a data classification per agent and per skill
for the model calls of their runs, and a model profile for agents created in the administration. It
builds on [agent control](ai-agent-control-plan.md), [agent skills](ai-agent-skills-plan.md),
[runtime overrides](ai-agent-runtime-overrides-plan.md) and the
[run configuration as data](ai-agent-run-configuration-plan.md). It was checked against `main` at
`6c152e0b` on 2026-10-22.

## Status

Implemented on 2026-10-22 and reviewed by Lars the same day. Sample case SPM-284 shows the off state
and `StartsOff()`, SPM-307 the data classification of a skill and of an agent created in the
administration. The consumer guide `ai-agent-runs` and the sample are authoritative from now on.
Every decision below is decided: the review changed O10, C1, C2, C5 and C6 and kept the others as
they were taken during the implementation.

## Problem

Pausing queues events per thread and resuming runs them all, which after weeks is a wave of stale
work. Stopping cancels running work, withdraws proposals and refuses chat. `Enabled(false)` in code
reads `configured-off` and cannot be switched on at runtime. None of them fits an agent or skill that
should simply not work on its own for a while, or that a deploy should bring in switched off until an
administrator switches it on.

## Decision record

One line per decision: the decision, the reason, and its review status.

| # | Decision | Reason | Review |
|---|---|---|---|
| O1 | The state `off` is stored in the existing `RunState` columns of the agent and the skill state; no migration. | The columns hold 16 characters and the state is one more value; a migration would add nothing. | Decided |
| O2 | Triggers ignored while off are reported as `ignored` with `agent-off` or `skill-off` (`NhAssistantTriggerReasons`), not audited, and not logged per event; a schedule reports one ignored receipt per tick without reading its subjects. | The request asks for the same treatment as `filtered`; one receipt per tick keeps the subjects query unevaluated. | Decided |
| O3 | What an agent takes on by itself is ignored while off: events, schedules, webhooks, follow-ups, hand-off answers and replays. Work a person asks for still starts: manual starts, messages typed in a thread and requests through another assistant. Continuations of accepted work (a resume, a move to the shadow thread) are not triggers. | Chat and `POST threads/start` must stay possible; a request is a person's start through another assistant. | Decided |
| O4 | A hand-off to an agent that is off is refused with `assistant-agent-off` (audited like other hand-off refusals) instead of being ignored. | The source's model and rules need to know that nobody took the work; a hand-off receipt has no ignored outcome. | Decided |
| O5 | A replay into a shadow variant that is off stops with `assistant-agent-off`, as it stops for a paused variant. | A replay is automatic evaluation work; an off variant should cost nothing. | Decided |
| O6 | Switching off cancels nothing: running runs and runs that were already queued finish with their inputs. | The request says running runs finish; a queued run was accepted work and pausing is what holds queued runs back. | Decided |
| O7 | Switching off ends the inputs that waited from an earlier pause, except those a queued or running run of the thread will claim; switching on from off never calls the resume of waiting inputs. | "Switching on replays nothing": events that waited during a pause would otherwise run weeks later. | Decided |
| O8 | A run whose rules route to a skill that is off ends `cancelled` with `assistant-skill-off` and nothing waits for the skill, as for a stopped skill; triage and `use_skill` already offer active skills only. | Rules must not route to an off skill, and an off skill keeps no backlog. | Decided |
| O9 | Switching on is `ResumeAsync` / `ResumeSkillAsync` (state `active`); only `SwitchOffAsync` and `SwitchOffSkillAsync` are new members. The administration labels the action "Switch on" for an agent or skill that is off. | `active` already means "works"; a second name for the same transition would make the state endpoint ambiguous. | Decided |
| O10 | The kill switch is `SetKillSwitchAsync` on `INhAssistantAgentControl`, which `POST admin/agents/{id}/kill-switch` uses. Engaging it stops the agent; a stop records whether the agent was off in the new `OffBeforeStop` column of `AssistantAgent` (migration `AgentOffBeforeStop`), and every other state change clears it. Releasing it never switches on an agent that was off: one that was off when it stopped goes back off and one that is off stays off, while every other agent resumes as before, a paused one included. Skills keep their own states throughout, and an explicit `ResumeAsync` still switches an agent on. `NhAssistantKillSwitchDto.RunState` reports the state after the change. | Decided by Lars: disengaging the kill switch must not switch on agents or skills that were off before it was engaged. Recording the off state at the stop survives restarts and leaves the explicit resume as it is. | Decided |
| O11 | Switching off is audited as the new kind `AdminAgentSwitchedOff` (62) with result code `off`; switching on as `AdminAgentRunsResumed` (`resumed-0`). There is no live channel for agent state; the administration updates from each action's response, as for the other states. | Same audit shape as the other state changes; the existing state changes have no live updates either. | Decided |
| O12 | `StartsOff()` applies when the agent row is inserted at startup. For skills, every skill in code gets a state row at its first start (active, or off with `StartsOff()`), so the row marks the skill as seen. A skill deployed before this version that gets `StartsOff()` in the upgrade deploy therefore starts off once. | A skill without a row was active, so "seen before" is unknowable for older skills; recording rows from now on makes later deploys exact. | Decided |
| O13 | Agents and data skills created in the administration start off only when asked to (`startsOff` on create, default `false`); the create forms offer "Switch on now", ticked by default. `startsOff` on a change of a data skill is a field error. | Consistent opt-in with `StartsOff()` in code and no change for existing callers; data skills already start in shadow. | Decided |
| O14 | An agent created off in the administration records its creator and time as the state change; a code agent that starts off has no change recorded, and the administration says it started off in code. | Shows who decided the state without inventing an actor for code. | Decided |
| O15 | `NhAssistantCodeRunSettingsDto.StartsOff` and `NhAssistantCodeSkillDto.StartsOff` show the starting state in code in the run configuration; the current state stays in the agent's state. | The administration can explain why an agent is off without mixing code and runtime state. | Decided |
| O16 | The sample deploys the project planner's evaluation variant off and extends SPM-284 instead of adding a case; its evaluation test switches the variant on and off again. | Evaluation variants are the natural "deploy now, switch on later" agents, and one control case keeps the registry free of duplicates. | Decided |
| C1 | The classification of a model call is the skill's, then the agent's, then `Internal`, for every model call of the agent: its runs, people's turns in its threads, its consultations and people's plain chat conversations with it; triage uses the agent's own. A plain chat moves to the profile's fallback that permits it or fails with `assistant-classification-not-permitted`. | Decided by Lars: a plain chat with an agent carries the agent's data as much as its runs do. | Decided |
| C2 | The enforcement stays the profile resolution, and a classification that no profile of the chain permits never refuses a save or a start. Saving such a data skill or agent created in the administration succeeds and its DTO reports `warnings` (`classification-not-permitted`, `NhAssistantConfigurationWarnings`): the administration shows it on the agent's card and in the agent editor, and for a skill with the saved message, on the skill and in the skill form. An agent, its triage or a skill in code with such a classification logs a warning at startup. | Decided by Lars: warn, don't refuse; the profiles may change without a deploy of the agent, and the turn's own check refuses the model call. | Decided |
| C3 | Before the model call the turn checks the profile and its fallbacks against the classification; when none permits it, the turn fails at once with the non-transient code `assistant-classification-not-permitted` (failure class `policy`, HTTP 400) and a run is not retried. The shared resolver itself is unchanged. | Decided by Lars: a denial is deterministic, so retries only cost time; checking in the assistant keeps the shared resolver's contract as it is. | Decided |
| C4 | The classification also classifies the skill's instructions asset and the run's hand-off tool calls; a consultation's own `DataClassification(...)` keeps classifying its answers in the asking conversation and is unchanged. | The hand-off message is the run's data; the consultation setting has its own meaning. | Decided |
| C5 | A data skill stores its classification as a name (`NhAssistantDataClassificationNames`, nullable, migration `SkillDataClassification`). An agent created in the administration chooses its classification in its definition next to its profile: `dataClassification` on the agent input and on `NhAssistantAgentRequest`, shown on `NhAssistantAdminAgentDto`, stored in the new nullable `DataClassification` column of `AssistantAgent` (migration `AgentDataClassification`); an unknown name is the field error `dataClassification: invalid` and omitted keeps it on update. Its plain chats and, with run settings, its runs use it. The agent editor offers it next to the profile and sends it only when it changes. | Decided by Lars: an agent created in the administration needs the choice an agent in code has with `DataClassification(...)`. | Decided |
| C6 | Sample case SPM-307: the document reader's `read-documents` skill is `Confidential`, so its model calls move from the chat profile to its fallback `project-assistant-confidential`, and an agent created in the administration chooses its profile and classification, with a confidential agent answering through the same fallback and a restricted one saved with the warning. The sample's budget manager records which profile served each model call as evidence. | Decided by Lars: the sample shows the classification of a skill and the administration's choice. | Decided |
| P1 | An agent created in the administration chooses its profile in its definition (`profile` on the agent input), stored in the existing `ProfileName`; not in its run settings. | The profile serves people's chat with the agent as well as its runs, and the column already exists. | Decided |
| P2 | The choosable profiles are exactly the run catalog's `Profiles` (registered, with chat, function calling and streaming), the set data skills choose from; any other name is `profile: not-found`, except the profile the agent has and the application's chat profile. | The administration may never pick an arbitrary or unconfigured model, one rule serves skills and agents, and a client that sends an agent back unchanged must not be refused when the chat profile lacks function calling or streaming. | Decided |
| P3 | Omitted on create uses the application's chat profile; omitted on update keeps the agent's profile; agents in code ignore it, as they ignore what they work on. | The same "omitted keeps" rule as the other administration-only fields. | Decided |
