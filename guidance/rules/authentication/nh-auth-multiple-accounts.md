## Preferred approach

Leave `AuthenticationNhCommonModuleConfig.multipleAccounts` off unless the application is an identity provider or portal whose users really hold several accounts. Off is the default: the browser keeps one authorization in `localStorage['at']`, a second sign-in replaces the first, and nothing else is stored or written. Opt in explicitly in the root configuration with `new MultipleAccountsAuthenticationNhCommonModuleConfig({enabled: true})`, as the sample's providers do (SPM-398). Every application on one origin shares `at` and the accounts, so configure the option the same way in each of them; an application that starts with the option off removes the accounts an earlier opt-in left in the browser, without revoking them.

With the opt-in, `at` keeps its meaning and shape as the active authorization, which every tab of the application shares, and `localStorage['nh-accounts']` holds the other accounts with their refresh tokens but never their access tokens. Every path that stores a session goes through `setAuthorization`, so a password sign-in, a second factor, an enrollment, a passkey, a renewal and a profile reload add or refresh the account without further code; a session without a refresh token, such as an impersonation, is never added. `accounts` lists them without any token, most recently used first, and `accountsChanged` emits whenever they change, also from another tab. The directory holds at most `maximum` accounts (8 by default); one more forgets the least recently used other account in this browser. A sign-in that fails leaves the active account signed in.

Renew a session with `renewSession()` instead of calling `authenticateRefreshToken` yourself. It takes one lock for every tab (the Web Locks API, or a short `localStorage` lease where the browser has none), reads the stored session again inside the lock, keeps a session that another tab just renewed or whose access token stays valid for more than a minute, and otherwise rotates the refresh token and stores the new session before the lock is released. Concurrent calls in one tab share one promise. When the refresh endpoint refuses a token that another tab rotated outside the lock, it returns the stored session instead of a failure. Pass the account you expect to be active as `userId`: the renewal then fails with `NhBrowserAccountFailureCodes.NotActive` when another tab switched meanwhile. Pass `{force: true}` when the server must write the access cookie again although the access token is still valid. `renewSession` also works without the opt-in, for the single session.

Switch with `switchAccount(userId)`: it always rotates the chosen account's refresh token, so the server checks again that the account may sign in and writes its access cookie, and then stores that session as the active authorization; reload the profile afterwards. Sign out one account with `logoutAccount(userId)`, which revokes exactly that account's refresh token and removes it from the browser also when the request fails. The browser's authentication cookies belong to the active account, so signing out another account sends `LogoutRequest.KeepAuthenticationCookies`: the standard logout endpoint then revokes only the token in the body, never the cookie's, leaves the cookies alone and confirms that with the `X-NH-Authentication-Cookies: kept` response header (`NhLogoutAuthenticationHandler.AuthenticationCookiesHeaderName`), which the platform's CORS policy exposes. A server that does not confirm it, such as an older one, expired the cookies; the active session is then renewed inside the same lock so its cookies are written again, and a failure of that renewal is part of the result. Deploy the backend first to avoid that extra rotation. `logout()` signs out the active account only, and `logoutAllAccounts()` revokes every account. `forgetAccount(userId)` removes another account from this browser without revoking it and resolves to `false` for the active account, whose session also lives in the server's cookies. `clearAuthorization()` ends the active account only; a session the server rejects, for example after a password change, ends every account of the browser. That decision is taken inside the session lock, so a 401 from the moment the cookies are expired while another account signs out does not end a session that was renewed meanwhile. Requests made inside the lock fail after 30 seconds, so no tab holds it for long. A profile that loads while another tab switched or signed out is not stored: `reloadAuthorizationProfile` then fails with `NotActive` instead of showing one account while the browser's session belongs to another.

Set `hintCookieName` only when a server-side authorize endpoint needs to know whether to show an account picker. The cookie holds the number of accounts and nothing else (`Path=/`, `SameSite=Lax`, `Secure` on https, the configured `cookieDomain`), lives as long as the longest refresh token and is removed when no account is left. Cookies ignore ports, so give each application on a host its own name. Treat it as a hint only: the session cookie and the `sub` of the issued token decide who is signed in.

A sign-in stores its session before the profile with its claims is loaded, so `isAuthenticated()` reports `false` until `reloadAuthorizationProfile` completes. With one account that window starts from a signed-out state; with several, a second account signs in while the first one is active. A session coordinator that routes to login on `sessionExpirationInformationChanged` must therefore treat a stored session with a refresh token, an access token that is still valid and no claims yet as a sign-in in progress, as the sample's `SampleAuthSessionService` does, and not clear it.

The refresh endpoint finds the account by its sign-in name. The service remembers the name typed at a password sign-in and otherwise uses the profile's `userName` or `email`; override `describeBrowserAccount` when the application signs in by another name.

## Avoid

- Enabling `multipleAccounts` as an incidental upgrade step; it widens what cross-site scripting on the origin can take from one refresh token to every account of the browser.
- Calling `authenticateRefreshToken` from two places, or from every tab that opens, instead of `renewSession`; the second call presents a consumed token and signs the person out.
- Renewing or signing out an account other than the active one with your own refresh or logout request; the server writes the browser's cookies for whichever account it renews, and a logout without `KeepAuthenticationCookies` expires them.
- Sending `KeepAuthenticationCookies` for the active account's own sign-out; that logout must end the cookie session too.
- Deciding who is signed in, or skipping authorization, from the hint cookie or from `accounts`.
- Keeping the directory after the server rejected a session, or copying refresh tokens out of the service into application state.
- Forgetting the active account to sign it out; its cookie session stays valid until `logout()` or `logoutAccount()`.
- Sharing one hint cookie name between applications that run on one host with different ports.
- Clearing the authorization from a session coordinator while a second account's sign-in is waiting for its profile.
- Configuring the option differently in applications that share one origin.

## Verification

In `nh-common` specs, sign in to two accounts and prove that both stay listed with their own refresh tokens, that the list carries no token, and that switching back and forth presents each account's own token and never consumes the other's. Start `renewSession()` twice in one tab and once in a second service instance on the same storage, with Web Locks and with the storage lease, and prove that exactly one refresh request is made and every caller receives the same session. Store a sibling's rotated token while a renewal is on its way and prove that a refused refresh resolves with the stored session. Prove that `logoutAccount` sends exactly that account's refresh token with `keepAuthenticationCookies`, keeps the active session when the server confirms it kept the cookies and renews it when the server does not, that `logoutAllAccounts` sends each token and keeps nothing also when one request fails, that `logout()` keeps the other accounts, that a 401 confirmed by the account endpoint clears the whole directory, that the hint cookie holds only the count and disappears with the last account, and that an invalid `maximum` or cookie name fails at startup. Prove that the directory holds no access token, that a profile which loaded while another tab switched, or which belongs to another account, is not stored, that an authorization mixing one account's profile with another account's refresh token changes neither entry, that a 401 during another account's sign-out keeps every account once the active session was renewed, that a directory changed outside the library and a lease claimed far into the future neither stop the application nor block renewals, and that an application with the option off removes accounts and a hint cookie left behind. With the option off, prove that a second sign-in replaces the first, that no directory or cookie is written, that a failed sign-in still ends the session and that the account methods refuse to run. On the server, call the standard endpoints over HTTP against SQL Server and PostgreSQL and prove that a logout revokes the presented token and expires both cookies without the confirmation header, that a logout with `KeepAuthenticationCookies` revokes only the token in the body while another account's token keeps refreshing, sets no cookie and confirms it, and that without a token in the body it revokes nothing, not even the cookie's token. The session lifecycle tests already prove that every login is an independent refresh-token session.
