## Preferred approach

Install and pin `NewHeap.Platform.DatabaseRead.Tool` in the consumer repository. Check in `.newheap/database-read.json` with a named provider, relative application configuration path, default environment, connection-string name, and limits selected by the implementing application for its diagnostic workload. Keep the selected connection string in the normal NewHeap appsettings and secret-substitution flow. It must use a dedicated database principal that can only connect and select from explicitly approved schemas, tables, views, and columns. NewHeap defaults and hard ceilings are fallback boundaries; they do not replace a deliberate consumer profile.

For a persisted-data question in a prepared consumer repository, take the direct database fast path. When the contract location is not already explicit, make one bounded tracked-file search from the consumer repository root for `**/.newheap/database-read.json`, `**/Tooling/DatabaseRead/README.md`, and `**/Tooling/DatabaseRead/requests/*.json` before declaring it missing. If exactly one catalog is found, use the directory containing `.newheap` as the diagnostic working directory, even when the local .NET tool manifest is in an ancestor directory. Treat the catalog, local database-read README and request files as the routing and query contract. Read the catalog only for non-secret routing metadata. When it contains exactly one profile, omit `--profile` or the JSON `profile` and let `newheap-db` select it automatically. The profile governs provider, configuration path, connection-string name and ceilings; its environment is the default runtime environment, not an environment allowlist. When the user explicitly requests another environment, pass `--environment <name>` to both schema and query commands. Do not refuse Production merely because the only profile defaults to Development, and do not require a duplicate profile solely to select another environment. Do not infer an override when the user did not name one. Let `newheap-db` resolve the governed connection-string name through the selected environment's normal NewHeap configuration and secrets flow; never read, echo or reconstruct the connection string. With multiple profiles, use the user's requested scope, a checked-in request's `profile`, or the local README to select one, and pass `--profile` when using direct schema discovery. Environment selection does not resolve an otherwise ambiguous profile choice. Ask only when those sources leave a real ambiguity. Load runtime configuration only after the bounded search finds no catalog, multiple catalogs remain ambiguous, or configuration itself is the subject of the task. Do not inspect controllers, entities, EF configuration, appsettings, secrets or NuGet package internals merely to discover choices or reconstruct request fields already declared by the contract. A local tool manifest entry does not prove that its package was restored; run `dotnet tool restore` only when invoking `newheap-db` reports that the command is unavailable.

`newheap-db validate` is local-only contract validation and opens no database connection. `newheap-db query` and `newheap-db schema` require outbound network access to the configured database. In Codex, invoke the first `query` or `schema` attempt with network-enabled or escalated execution instead of probing the restricted sandbox. Use a narrow reusable permission rule scoped only to `newheap-db`, such as the `dotnet tool run newheap-db` prefix; never grant a general `dotnet`, shell or outbound-network prefix for this workflow. Treat a `network-access-required` retry hint as capability metadata, not proof that a Codex sandbox caused the failure: firewalls, DNS failures and network ACLs can produce the same result. An untrusted server certificate is not a network failure: it returns the non-transient classification `tls-certificate-untrusted` with stage `connection-open` and the retry hint `certificate-authority-trust-required`. Trust the certificate authority that issued the database server's certificate on the diagnostic host, or have the server present a certificate from an authority the host already trusts; do not retry, and never switch on `TrustServerCertificate` or lower the PostgreSQL `SslMode` to get past it. SQL Server keeps the SSPI code, such as `-2146893019`, as `providerCode`; PostgreSQL has no SQLSTATE for it. Npgsql and SQL Server's managed network layer do not say which certificate check failed, so there a certificate rejected for its host name or validity period reports the same classification.

For unknown deployed identifiers, call `newheap-db schema --search <term> --describe-if-single`, optionally with `--schema-name <name>`. This direct route creates the schema request internally. It returns full columns, indexes and relationships when the bounded search has exactly one untruncated match, using the same verified connection and read-only transaction; zero or multiple matches return bounded summaries for one refinement. Do not look up a schema-request JSON shape or create a temporary schema file first. For the data query, send one schema-versioned JSON request through standard input or pass its path with `--request-file`, and consume the single JSON response from standard output. Prefer a structured MCP call for agent diagnostics. For direct CLI use, pass only the request path or stream the JSON; never inline serialized JSON in `powershell -Command`, `cmd /c`, `dotnet run` arguments or another process-launch string. A transport limit must not cause the caller to narrow an otherwise correct predicate or candidate set. Put every data value in the typed `parameters` collection and refer to it by name from SQL. The `schema` and `query` commands perform request validation internally. Do not run `validate` immediately before either command during an interactive diagnostic; reserve it for CI, checked-in template validation or another intentional dry run. An exact description returns permission-filtered named outgoing and incoming relationships. Each relationship identifies its source and target object, gives the source/target column pairs in declared order, and reports whether the database has validated the constraint, so callers can construct joins without guessing physical foreign-key mappings. An unvalidated relationship is useful structural metadata but is not an integrity guarantee for existing rows. The focused `indexes` operation can provide one quick query-design hint for an exact, already-confirmed object when table size, predicate selectivity or ordering cost is uncertain. Index responses expose uniqueness and primary-key markers, an optional partial predicate, positioned key entries with direction and kind (`column` or `expression`), and included columns only when the read-only principal can select the required objects and columns. Column keys carry a name; expression keys carry the provider expression. Schema responses include a content hash and do not expose view definitions, default expressions or stored routines.

A non-success response from the governed schema command is terminal for that diagnostic attempt, with one narrow local-host exception. When the stable code is `connection-string-unresolved`, inspect only the non-secret `NewHeap.PlatformCommon.AppSecretsDirectoryPath` routing values when needed. If checked-in local instructions already give the exact directory, or an existing local secrets-root environment variable can be joined with the configured deployment path's service-directory suffix without scanning, set `NewHeap__PlatformCommon__AppSecretsDirectoryPath` only in the `newheap-db` child process and retry the same schema command once. This is appropriate when Production application settings intentionally contain a Linux secrets path while diagnostics run on Windows. Do not read secret or connection-string values, scan candidate secret directories, or persistently edit application settings. Continue to a query only if that single retry returns the required schema evidence. For every other schema error, or when the safe local path is not already determined, report only the stable error code, safe message and request identifier, then stop. Do not inspect source code, a repository index, entities, enum values or EF mappings as secondary evidence for deployed physical identifiers or business semantics, and do not construct or execute a data query after the failed schema call. A schema failure establishes neither deployed identifiers nor relationships and can indicate configuration or connectivity that a query cannot bypass.

When an application exposes diagnostics to an agent through MCP, publish separate schema, indexes and query tools through a consumer-owned governed catalog. Keep relationships in exact schema descriptions instead of adding another tool call. Make the indexes tool describe one exact, already-confirmed object and explain that callers use leading key position and direction to design selective predicates and compatible ordering; included columns are coverage hints, not predicate keys. Fix the profile, authorization scope, capability, call budget, maximum row ceiling and timeout in the MCP server. Let the caller state the rows requested within that ceiling, reject a higher value before execution, and pass the exact accepted value to `maximumRows`; never silently reduce it. Validate each request before execution, retain the NewHeap provider response as structured data, and map failures from the stable classification and provider code rather than forwarding raw database messages. The SampleProjectManagement MCP application is the executable reference and deliberately permits up to 1,000 requested rows and sixteen calls for its sample workload.

When a debugging request concerns unexpected persisted state, missing or incorrect records, an API/database discrepancy, or unexplained staging or production behavior, use the supported read-only tool directly when database evidence could materially answer the question and the requested scope authorizes the local diagnostic. Do not wait for the user to name the tool and do not stop after merely offering it. For a simple count/latest or record lookup, make one direct schema invocation, at most one process-local retry for the exact unresolved-secrets-path case above, and, only after schema discovery establishes the required identifiers and relationships, one query invocation. Report the selected profile and provider plus the bounded evidence that answers the question, and stop. Do not repeat a completed call or branch into unrelated source investigation or data access; a general debugging request does not broaden the requested environment or diagnostic scope.

Treat both staging and production as live, shared systems whose tables may be large. Select only the required columns, use selective parameterized predicates, and put a provider-native row cap in every diagnostic data query: `TOP` for SQL Server or `LIMIT` for PostgreSQL. Also set request-level `maximumRows` and `timeoutSeconds` values no larger than the consumer profile. The application may deliberately permit larger interactive investigations, including around 1,000 rows, when its output, timeout, authorization and data-classification boundaries support that workload. A query that produces more rows or output than the accepted request limit fails without a partial result; callers must narrow it or explicitly request a permitted higher limit.

When table size, predicate selectivity, or ordering cost is uncertain, optionally make at most one focused `indexes` request for the relevant already-confirmed object. If a suitable leading key and compatible ordering are immediately clear, use them. Treat included columns only as projection coverage. Use a partial index only when the complete query predicate demonstrably implies its reported predicate, and use an expression key only when the query applies a semantically compatible expression and ordering. Do not spend follow-up calls choosing among ambiguous indexes or turn the diagnostic into a performance-tuning exercise. If no directly useful index is reported or metadata is unavailable, continue with a parameterized predicate, provider-native row cap, bounded request limits and timeout. Stop only when a safely bounded query cannot be formed or the query reaches its statement or lock timeout; never compensate with a broader predicate, larger row cap or longer timeout.

Treat schema filtering, the query parser, SQL Server `ApplicationIntent=ReadOnly`, PostgreSQL read-only transactions, timeouts, row limits, output limits, and rollback as defense in depth. The database permission model is the security boundary. An environment override changes only runtime configuration resolution; schema and query still reject a connection whose principal has write, DDL or elevated permissions. Provider failures return only stable classifications and allowlisted PostgreSQL SQLSTATE or SQL Server numbers; never expose the raw provider message. Prefer a read replica or masked diagnostic views when production data is sensitive.

For principal rejection on either provider, the stable code remains `read-only-principal-not-verified` and exit code remains 4. The optional `error.verificationCheck` identifies the first rejected permission-policy check, for example `database-role-db_owner`, `procedure-execute` or `function-select` on SQL Server and `predefined-role-membership` or `catalog-function-execute` on PostgreSQL, with stage `readonly-verification`. It does not enumerate all rejected checks or expose principal, object or connection names. Consumers may preserve known check identifiers in diagnostics; accept an absent field from older tools, which report it only for SQL Server, and discard unknown identifiers instead of forwarding arbitrary text. The SQL Server function policy is deliberately strict: SELECT or EXECUTE on any user-defined function, scalar, inline or multi-statement table-valued, or CLR, rejects the principal with `function-select` or `function-execute`, because the tool does not verify what a function depends on or whether it has side effects. A function SELECT rejection describes that conservative policy, not proof of write access. Grant the diagnostic principal no function or procedure permissions; expose the data it needs through table, view or column grants instead.

On SQL Server the verification checks the effective permissions of the login and the database user, including those held through roles, ownership and implication. After the role and permission checks above it rejects `VIEW SERVER STATE`, also through `##MS_ServerStateReader##`, with `server-permission-view-server-state`; `ALTER ANY CONNECTION`, `IMPERSONATE ANY LOGIN` and `ALTER ANY SCHEMA` with their own `server-permission-*` or `database-permission-*` check; IMPERSONATE on a login or a user with `login-impersonate` or `user-impersonate`; UPDATE on a sequence with `sequence-update`; ALTER or TAKE OWNERSHIP on a schema or an object with `schema-permission-alter`, `schema-permission-take-ownership`, `object-permission-alter` or `object-permission-take-ownership`; and column-level UPDATE with `column-update`. It then denies by default: on the server, the database, a schema, an object, a column, a login, a server role, a database principal or another database securable, any permission the server knows other than connecting, SELECT, metadata visibility (`VIEW DEFINITION`, `VIEW CHANGE TRACKING`, `SHOWPLAN`) and the column-key definitions that every database grants to public rejects the principal with the matching `*-not-allowlisted` check, for example `VIEW DATABASE STATE`, `UNMASK`, `REFERENCES` or ALTER on a role. The empty schemas of fixed database roles are skipped, so `db_datareader` membership still passes.

On PostgreSQL the verification denies by default and covers the connected role and every role it is a member of, also a membership without inheritance, because the principal can switch to such a role. Beyond the privileges the server granted when it was initialized, the principal may hold only SELECT on tables, views, sequences and columns, and membership in `pg_read_all_data`. Membership in any other predefined role, including `pg_monitor`, `pg_read_all_stats`, `pg_read_all_settings`, `pg_signal_backend` and the server-file roles, rejects it with `predefined-role-membership`. A role attribute such as CREATEROLE, ownership of the database or of any schema, relation, function or type, CREATE on the database or a schema, any other table, view, column or sequence privilege, EXECUTE on a function outside `pg_catalog` and `information_schema`, and EXECUTE on a `pg_catalog` function that the server does not grant to PUBLIC, such as `pg_stat_reset` or `pg_ls_logdir`, reject it as well. Schema names are compared exactly, so a user schema whose name merely starts with `pg` is checked like any other.

## Avoid

- Passing SQL data values, connection strings, passwords, tokens, or secrets in command-line arguments.
- Declaring the profile catalog missing from the current working directory before the bounded tracked-file search, or treating an ancestor tool-manifest directory as the diagnostic root when the only catalog is nested below it.
- Asking the user to choose an environment when the user already named one, or when the profile default, a checked-in request or the local README already supplies the intended scope.
- Refusing an explicitly requested staging or production diagnostic merely because the selected profile defaults to another environment, or requiring a duplicate profile solely for that environment instead of passing `--environment` consistently to schema and query.
- Inferring an environment override that the user did not request, or treating `--environment` as permission to change the profile's provider, configuration path, connection-string name or ceilings.
- Reading or printing the resolved connection string instead of letting `newheap-db` resolve the selected profile's connection-string name.
- Inspecting application code, appsettings, secrets or package internals to rediscover a profile or request contract that the consumer repository already declares.
- Falling back to source code, a repository index, entities, enum values or EF mappings after a governed schema error, or issuing a query based on inferred deployed identifiers or business semantics.
- Persistently changing a Production secrets path for a local diagnostic, guessing or scanning secret locations, or retrying more than once after a process-local secrets-path correction.
- Looking up or authoring schema-request JSON before trying the direct `schema --search ... --describe-if-single` route, or running a redundant `validate` immediately before `schema` or `query`.
- Treating `dotnet tool list --local` as proof that the pinned tool was restored, or restoring packages before the command reports that the local tool is unavailable.
- Putting serialized request JSON in a shell or process argument, or changing query semantics to work around a host command-line limit.
- Concatenating a value into SQL or representing an identifier as an unrestricted input parameter.
- Reusing the application owner, migration, administrator, `db_owner`, `db_datawriter`, superuser, schema-owner, or procedure-execution credential.
- Guessing physical identifiers from domain names when the repository or typed schema command can establish them.
- Running `SELECT *`, an unbounded data query, a broad `COUNT(*)`, an avoidable full scan or sort, or `EXPLAIN ANALYZE` against staging or production merely to discover what is present.
- Trying `query` or `schema` in a restricted Codex sandbox before requesting the narrow `newheap-db` network permission, or broadening that permission to arbitrary `dotnet` or shell execution.
- Treating the client-side row limit as a substitute for `TOP` or `LIMIT` in the SQL sent to the database.
- Silently lowering an excessive caller request or presenting a truncated query result as successful.
- Treating the tool as a reporting exporter, scheduled job runner, migration mechanism, data repair path, or substitute for application authorization.
- Returning provider exception text, configuration values, stack traces, or other secret-bearing diagnostics in JSON errors.
- Retrying a `tls-certificate-untrusted` failure, or getting past it with `TrustServerCertificate`, a lower PostgreSQL `SslMode` or another switch that turns certificate validation off.
- Granting the diagnostic principal SELECT or EXECUTE on a user-defined function to make a read work; the strict function policy rejects it.
- Granting the SQL Server diagnostic principal `VIEW SERVER STATE`, `VIEW DATABASE STATE`, `ALTER ANY CONNECTION`, IMPERSONATE, UPDATE on a sequence, ALTER or TAKE OWNERSHIP on a schema or object, or any other permission beyond connecting, SELECT and metadata visibility; verification rejects it.
- Granting the PostgreSQL diagnostic principal a predefined role other than `pg_read_all_data`, such as `pg_monitor` or `pg_signal_backend`, EXECUTE on an administrative `pg_catalog` function, or membership in a role that holds more than SELECT; verification rejects it.
- Letting an MCP caller choose the database profile, connection string, authorization scope, operational ceilings or diagnostic credential.
- Treating included columns as predicate keys, ignoring composite key order, or assuming an unreported index is accessible.
- Guessing join columns when an exact schema description can establish the named relationship and ordered source/target pairs.
- Treating an unvalidated relationship as proof that every existing row satisfies the foreign-key mapping.
- Using a partial index when the query predicate does not imply the complete reported predicate, or treating an expression key as an ordinary column key.
- Assuming a lexical read-only check can replace SQL Server and PostgreSQL permission tests.

## Verification

Validate strict JSON parsing, typed schema and parameter conversion, query-policy rejection, request and output bounds, stable error codes, environment-override validation, and canary-secret non-disclosure without a database. Prove `validate` opens no connection and returns `requiredCapabilities: ["outbound-network"]`. Use an injected connection factory to prove that socket, DNS and unknown provider failures at connection open become `connection-failed` with the first safe provider code, `connection-open` stage, transient status and `network-access-required` retry hint without real network access. Prove authentication and database-selection failures remain `authentication-failed` and `database-not-found`; never expose a server name, credential, provider exception message or stack trace. Prove an untrusted certificate chain becomes the non-transient `tls-certificate-untrusted` with the `certificate-authority-trust-required` retry hint and stage `connection-open` on both providers, keeping the SQL Server provider code, separately from rejected credentials and network failures, with canaries proving that neither the certificate subject nor the provider message is returned; prove it through a real TLS handshake on each provider as well: SQL Server with certificate validation on against a self-signed server certificate, and Npgsql with `SslMode=VerifyFull` against an endpoint whose certificate no authority on the host trusts. Prove an unresolved NewHeap secret reference returns `connection-string-unresolved` with the process-local secrets-path remediation, while malformed resolved provider configuration returns `connection-configuration-invalid`; neither response contains schema, result data or the offending value. Keep checked-in typed schema and bounded parameterized query requests as repeatable CI contracts, and validate both through `--request-file` without opening a database. Include a Codex eval that requires the first `query` or `schema` attempt to use narrow `newheap-db` network-enabled execution without an initial restricted-sandbox probe. Include a monorepo routing eval with a tool manifest at the repository root and exactly one catalog under a backend directory: the agent must find that catalog in one bounded tracked-file search, use its directory as the working directory, select its only profile without an environment question when the user did not name another environment, and let `newheap-db` resolve the configured connection-string name without inspecting or exposing its value. Add a production regression prompt where that only profile defaults to Development: the agent must pass `--environment Production` to exactly one schema and one query invocation, must not demand a separate production profile, and must still rely on read-only-principal verification. Add an unresolved Production secrets-path prompt that permits one process-local `NewHeap__PlatformCommon__AppSecretsDirectoryPath` correction from already-declared non-secret routing metadata, one schema retry and then a query only after successful schema evidence. Add another failed-schema prompt that requires a terminal safe report without a query, source/index fallback or inferred identifiers. Launch the real tool process with `--request-file` and a valid payload larger than the Windows process-argument limit, prove only the short path is passed as an argument, and prove unavailable request files return a stable error without revealing their path. Keep stdin behavior covered for compatibility. On real SQL Server and PostgreSQL instances, prove the explicit environment is reported while direct search-and-describe uses one verified connection and read-only transaction, returns full metadata only for one untruncated match, and executes a parameterized and SQL-bounded `SELECT` through the public tool entry point with a dedicated read-only login. Also search and describe schema separately and request index metadata for compatibility. On both providers, prove a schema search through the provider and the CLI with the schema omitted, the search term omitted, both omitted and an explicit schema, and a search-and-describe without a schema, with unselectable objects still absent and the row limit still truncating. Prove named outgoing and incoming relationships with validation status and ordered pairs for single and composite foreign keys, and prove a relationship is omitted when the principal cannot select either endpoint or a paired column. Prove positions, kinds, names or expressions, direction and included columns for real composite, partial/filtered and expression/computed indexes, including the optional predicate. Prove inaccessible objects remain absent, missing objects and columns plus denied reads return only their allowlisted provider classifications and execution stages, row overflow fails without result data, and a direct `UPDATE` with that same credential fails. On real SQL Server, prove the same one grant at a time for `VIEW SERVER STATE` granted directly and through `##MS_ServerStateReader##`, `ALTER ANY CONNECTION`, `IMPERSONATE ANY LOGIN`, IMPERSONATE on a login and on a user, `ALTER ANY SCHEMA`, UPDATE on a sequence, ALTER and TAKE OWNERSHIP on a schema and on a table, column-level UPDATE, `VIEW DATABASE STATE`, REFERENCES on a table, ALTER on a role and ALTER on a login, each with its own verification check, and prove `db_datareader` and database-level SELECT, VIEW DEFINITION and SHOWPLAN still pass. On real PostgreSQL, prove that the SELECT-only principal passes and that one grant at a time, each taken back before the next, is rejected with its own verification check: each predefined role listed above directly and through a group role, a membership without inheritance in a role with CREATEROLE, EXECUTE on a `pg_catalog` function revoked from PUBLIC granted to the principal and to PUBLIC, a function in a user schema named `pgx`, a column-level UPDATE, an INSERT on a view, an UPDATE on a table, USAGE on a sequence and ownership of a table; prove `pg_read_all_data` still passes. Exercise provider-specific locking and statement timeout setup separately, and verify the diagnostic examples use `TOP` or `LIMIT` in addition to request-level row and timeout limits. For an MCP wrapper, use the official in-memory transport against a real provider and assert that only the governed schema, indexes and query tools are listed, relationship and index evidence are returned before query construction, a query executes through the dedicated read-only principal, sixteen calls are available per sample invocation, a request above the consumer ceiling fails before execution, and an actual result above the accepted request limit fails without partial data.
